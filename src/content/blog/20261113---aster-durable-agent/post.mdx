## 我要的不是聊天窗口

过去三个星期，我给自己做了一个叫 Aster 的助手，跑在腾讯云的一台小规格服务器上。一开始它只是我的 Telegram 私聊 bot：一个人、一个会话、一份记忆。很快我就把它接到了 Slack。现在的界面是 Slack：我可以在单聊里用，白名单频道里的成员也可以 @ 它提问，在它的回复下面继续追问。每个人有自己的 Hub——独立的会话、记忆和工具集。进程被杀掉之后，它还能从落盘的状态里恢复，接着干没做完的事。

代码在 [GitHub](https://github.com/NaoYUN77/Aster)。底座是 `pi-durable`，运行时是 Node.js，状态放在 SQLite 里，生产形态是单个 Docker 容器。它已经在这台机器上持续运行。

我要的不是再开一个聊天窗口，而是一台可以过夜的助手：挂在无头小机器上，不对外暴露入站端口，进程偶尔会被杀，运维的人只有我自己。现在还多了一条约束：频道里不能把所有人的上下文混在一起。这些后来几乎决定了每一项技术选择。

## 一条消息怎么走完

一条消息在 Aster 里走的路，现在是从 Slack 开始的：

```text
Slack Socket Mode
  → 入向策略（白名单；身份只取 event.user）
  → 频道里 @ 提问，或在回复线程里追问
  → 先写入 inbox（带上线程锚点），再确认消费
  → 路由到这个人的会话
       所有者 → root Hub
       成员   → 自己的 Hub
       线程追问 → 该 Hub 的 fork
  → 使用这个 Hub 的记忆
  → 调用模型，执行这个 Hub 的工具集
  → 回复先落盘，再按同一线程锚点分段发回
```

接入走 Socket Mode，是出站长连接，容器不必对公网开放入口。谁可以驱动 bot、在哪些频道里回话，写在启动配置里，事件不能给自己扩权。身份只取 Slack 传来的 `event.user`，消息正文永远改不了「我是谁」。单聊只服务我本人；频道里必须先 @ 才开一场新对话，零散消息不算。已经在回复线程里的追问不必再次 @，答案也回到同一条线程。

有两处不太符合直觉。

第一，请求是串行的。同一时刻只处理一条，Hub 之间也不并行；同一回合里的工具顺序执行，避免共享目录上的读写交错。单条请求最多等五分钟，超时就向底座请求取消，外部副作用并不保证能收回。同一份数据目录还用 `flock` 卡住，只允许一个进程。

第二，投递失败不会把 agent 再跑一遍。Slack 发出去的消息没有我能用的幂等键，超时既可能没发出去，也可能对面已经收到了。结果未知的分段因此不会自动重发，需要我对着频道记录选择「再发一次」或「就当已送达」。漏一条或偶尔重复一条，都比把已经做过的工具调用再跑一遍更可接受。

## 隔离不靠提示词

如果把所有人放进同一个会话，再在提示词里写「别去读别人的东西」，我认为不可靠。提示词注入就可以冒充身份；`memory_search` 一旦搜到我的日常记录或画像，隔离也就只是一句嘱咐。所以 Aster 的隔离是结构上的，不是口头上的。

每个人第一次被允许进场时，会得到一个自己的 Hub。成员标识来自传输层，目录按这个标识派生：会话将来若被重建，记忆和文件仍然跟着这个人，而不是跟着某一个会话号。

- 会话是独立的 pi-durable Conversation。
- 工作目录在 `workspace/members/<memberId>`。我自己的仍是 `workspace/`。
- 记忆根目录在 `memory/members/<memberId>`。我自己的仍是 `memory/daily`。
- 工具策略在创建会话时用 `tools.remove` 固定，之后的请求放不宽。

记忆这一层尤其不能含糊。整个进程里仍然只有一套记忆工具，但 store 按会话解析。Hub 和它的线程 fork 登记到同一个人的根目录，子会话因此读得到这个人的长期记忆。未登记的会话会直接报错，绝不回落到别人的、或我的 store。成员之间，以及成员和我之间，每日记录和画像因此互不可见。

工具集也按 Hub 切开，收回的是能力，不只是名字。成员没有 `bash` 和 `powershell`——这是同一种壳能力，换个宿主名字也不能留。提醒工具也不给成员：提醒的目标聊天是宿主写死的，目前固定发到我的会话，给出去只会发错人。skills 是宿主侧的规程，同样只在我的 Hub 里开放。创建时拿掉的工具，模型根本调不到。

成员并不是什么工具都没有。他们可以用记忆工具回忆自己先前问过的事，处理自己工作目录里的文件，也可以使用网络工具和已接入的 MCP；浏览器或表情回应若已部署，同样会出现在成员的 Hub 里。我自己的 root Hub 保留全套工具，也没有回合上限。

线程是 Hub 上的 fork，不是一个全新的人。追问从 bot 那条回复接着聊，工具策略、指令和记忆 store 逐字继承。一条线程最多五个回合，到顶后由宿主把子会话自己的回合摘录写回 Hub——不另调一次模型——再结束这个 fork，并附上一句「该问题循环过多，请不要再回复。」之后同一线程不再进模型；新的 @ 提问会从 Hub 重新 fork，靠这个人已有的历史和长期记忆续上。信息向上汇聚：fork 读得到 Hub 的长期记忆，Hub 只能通过那条有界摘要看到线程里结算过的内容。

这套隔离仍有我故意留下的缺口。成员的 `read` / `write` / `edit` 如果被指向绝对路径，理论上仍可能碰到数据目录里不属于他的文件；网络工具也还在。当前的前提是：进得了白名单的都是自己人。按 Hub 收紧文件系统，是下一步的事，不是现在已经做到的事。

## 每个 Hub 都有自己的分层记忆

隔离解决的是「记在谁那里」。每个 Hub 内部，上下文仍然分成三块，为的是跨轮、跨日还能接着干活，同时控制输入规模和前缀变化：

- **A：稳定规则。** 系统提示和工具声明。尽量保持不变，好让模型提供商的前缀缓存生效。
- **B：周期快照。** 连续性摘要，加上这个 Hub 的 working 基线。只在压缩或重置真正生效时切换。
- **C：实时尾巴。** 近期原文、工具结果，以及这一轮检索到的内容。

```text
请求 n     A | B7 | T1 ... Tn
请求 n+1   A | B7 | T1 ... Tn | Tn+1
压缩生效   A | B8 | 保留的近期流水 ...
```

Aster 刚能对话的时候，长期事实放在一份 `workspace/MEMORY.md` 里。分层记忆接上之后，同一类事实出现了两条通道，模型得自己挑写哪边。于是我停掉了它：应用不再创建，也不再要求模型读写；磁盘上的旧文件原样保留，只是不再被使用。现在，常驻目标、约束和偏好进这个 Hub 的 working memory，过去的事实用 `memory_search` 检索它自己的每日归档。

这样切，不完全是为了结构好看。我在腾讯云那台 4 核、内存 7680 MB 的机器上做过补测——设计文档里的基线是 4 GB，验收机更大一档；峰值 RSS 大约 136 MiB，离 4 GB 还很远。用 DeepSeek 沿着真实集成链路跑了十轮中文对话：28 次调用里 27 次命中云端前缀缓存，大约 87%。唯一没命中的是前缀变更之后那一次，和压缩切到新周期的预期一致。这是一次 DeepSeek 补测，不是「所有模型都会这样」的保证。

机制跑通了，质量上还是撞过墙。有一阵模型反复调用 `working_update`，却总被「证据条目不在当前对话里」拒绝。根因很简单：entry id 根本不会出现在模型看得见的 transcript 里，它只好猜，参数里经常是 `evidence: [1]`。后来我让 `working_read` 列出最近几条用户条目的真实 id，校验失败时也带上同样的列表。摘要和归档还会把没给过的年份补出来，同一份日记里甚至前后矛盾，于是提示词加了规则：原文没有的年、月、日，不许发明，也不许补全。

还有一个我还没改的缺陷：回复已经落盘，但收尾计数还没跑，进程就被杀掉，这一轮会永久少记一次。回复本身是完整的，只是压缩评估点会后移一轮。用户画像仍是观察期做法：暂存在该 Hub 的 working memory 里，从它自己的每日归档提取，不另开一轮模型调用。

## 无头机器上的接入选择题

Aster 跑在腾讯云的无头机上，没有浏览器，也没有图形界面。不少「官方推荐」的接入方式，在这台机器上自然不成立。

渠道是第一道题。Socket Mode 让 Slack 事件从出站连接进来，容器不必开放入站端口。这台机器上，`slack.com` 和 `wss-primary.slack.com` 可以直连，出站需要时仍可走 MITM 代理。最早做 Telegram 时还要担心直连不到 `api.telegram.org`；现在界面换了，不开入站端口这条纪律没有换。

MCP 是第二道。本地 stdio 加上 token 是默认路线：进程由 Aster 拉起，凭据走环境变量，不需要浏览器。远程 OAuth 我没有丢掉，但授权不在服务器上做——在有浏览器的环境跑完 `mcp:auth`，再把 token 文件部署过来，或用 SSH 隧道把回调打回服务器。我拿 Notion 的托管 MCP 做过一次实测，前面都走通了，换 token 时对面返回 502，后来判断是对方服务故障，这条验证就搁下了。

密钥托管也碰过一次墙。我曾经接入过一套 Agent Vault 和出口路由器，选的是 Infisical 云；从这台中国区机器根本连不上，那条注入链从未真正启用。与其维护一套默认关闭的子系统，我后来把它整段删掉，凭据改放在受限的环境变量里，应用只做存在性和形状校验。再往后，出站 HTTPS 可以走 OpenBao 的 MITM 代理，应用进程里只看到占位符。浏览器的调试端口只绑在另一台机器的回环上，经一把只能转发、拿不到 shell 的 SSH 钥匙进来；GitHub 的 webhook 先打到 Cloudflare Worker，应用再去长轮询拉取。容器始终不对外暴露入站端口。

## 加过，也删过

不是每项做出来的能力都该留在主助手里。

10 月底到 11 月初，我给远程执行做过一茬相当深的工作：主机侧的 broker、常驻 RPC、脚本式的工具入口、远程沙箱。需要分清的是：`pi-durable` 的 Session、checkpoint 和重放一直在，那是助手能过夜的底座，没有动。被拿掉的是另外一套远程执行与沙箱。后来那套独立部署归档了，我把相关代码和编排从主仓库整段拆除，主助手回到单个容器。功能多，并不等于这台机器上的助手更强。

对照留下来的选择，逻辑是一致的。状态放在 Node 内置的 SQLite 和每日 Markdown 里，不另起数据库或向量服务；每个 Hub 多一份会话和一份日记，代价可以接受，不必为此换存储。工具检索先用 BM25，语义检索等到真有信号再评估——现在工具量还小，再加一条出境或本地嵌入依赖，对单人运维并不划算。一次性提醒也是独立的 SQLite 状态机，在同一进程里调度，目标聊天由宿主写死。应用停机期间到期的提醒不会发出去，恢复后会补发，可能晚于原定时刻。这些都是故意接受的代价。

## 先把该留下的写到磁盘上

Aster 现在能做的事，和它故意不做的事，一样值得说清。请求是串行的，频道里同时有几个 Hub，它们之间也不并行，忙的时候消息会留在 Slack 一侧。`bash` 不是沙箱，只出现在我自己的 Hub 里；成员侧的文件工具也还没有按目录封死。CI 覆盖类型检查、离线测试和镜像边界，但不覆盖从 Slack 到模型再到投递的完整业务链。这些不是「还没来得及写」，是当前的边界。

接下来我想分开写的，是 skills 的延迟加载，以及事件跟踪真正跑起来之后的体验。那些适合另起一篇。

如果你也在给自己做一个要跟许多人共用的助手，欢迎直接看仓库。我想讲清的只有两条：按人隔离靠的是会话、目录和工具集，不是提示词；先把该留下的状态写到磁盘上，再去跟不可靠的网络、以及可能被杀掉的进程打交道。
